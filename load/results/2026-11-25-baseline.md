# 기준 부하 측정 (2026-11-25)

2단계의 출발점. 동시에 진행되는 연습 수를 올려 가며 처리량, 응답 시간, 먼저 막히는 곳을 본다. 특정 장비의 최대치를 재는 것이 목적이 아니다.

## 조건

| 항목 | 값 |
|---|---|
| 장비 | MacBook Pro M3 Pro(11코어, 18GB), Docker Desktop 메모리 11.7GB·CPU 11개 |
| 컨테이너 상한 | backend 2 CPU·1GiB, mysql 2 CPU·1GiB, payment-mock 1 CPU·512MiB, frontend 0.5 CPU·128MiB |
| 백엔드 | JVM 25, 커넥션 풀(Hikari) 기본 10개, 격리 수준 READ COMMITTED, 가상 경쟁자는 가상 스레드 |
| MySQL | 8.4, 기본 설정 |
| 모의 결제 서버 | 승인 1~3초, 가상 스레드 |
| 부하 도구 | k6(`grafana/k6` 이미지), `load/baseline.js`, `load/run-baseline.sh` |
| 시나리오 | 가상 사용자 한 명이 연습 한 번을 처음부터 끝까지: 닉네임 → 연습 시작(어려움) → 오픈까지 10초 대기 → 입장 → 좌석 상태 → 좌석 누르기(거절되면 다른 좌석, 2석까지) → 선택 완료 → 가격 확인 → 금액 → 결제. 각 단계 2분 |
| 동시 연습 상한 | 측정하는 동안 1000으로 풀었다 |

부하의 대부분은 k6가 아니라 서버 안의 가상 경쟁자에서 나온다. 어려움 난이도는 연습마다 가상 경쟁자 1,000명이 25초에 걸쳐 들어와 좌석을 누르고 결제한다. 그래서 "동시 연습 N개"는 서버 안에서 최대 N×1,000명의 가상 경쟁자가 겹친다는 뜻이다.

두 조건으로 쟀다.

- **곧바로 누름**(입장 뒤 쉬는 시간 0초): 사용자가 오픈 직후 2초 안에 예매를 끝낸다. 사용자가 성공하면 그 회차의 가상 경쟁자가 멈추므로, 가상 경쟁자 부하가 일찍 끊긴다(가장 가벼운 쪽).
- **사람처럼**(입장 뒤 10초 쉼): 쉬는 동안 그 회차의 가상 경쟁자가 거의 모두 움직인다. 어려움은 약 10초에 매진되므로 사용자는 대부분 매진을 만난다(실제에 가까운 쪽).

같은 순간에 실제로 겹치는 부하는 "동시 연습 N개"보다 낮다. 연습마다 처음 10초(오픈 대기)에는 가상 경쟁자가 움직이지 않기 때문이다.

## 먼저 막힌 곳

**DB 커넥션 풀**이다. 근거:

1. 풀은 10개인데 연결을 기다리는 스레드가 수천에서 2만 개까지 쌓였다(표의 "풀 대기"). 사람처럼 10개에서 이미 평균 1,830개다. 쓰는 중인 연결은 대부분 10개에 붙어 있었다.
2. 백엔드 로그에 연결을 30초 안에 얻지 못한 오류(`HikariPool-1 - Connection is not available, request timed out after 30000ms`)가 측정 전체에서 12,512건 남았다.
3. 가장 먼저 느려진 요청은 DB를 가장 자주 쓰는 좌석 상태와 좌석 누르기다. 결제 요청(대부분의 시간이 모의 결제 서버의 1~3초)은 20개에서도 3초 안이었다.

원인은 가상 경쟁자가 수가 정해지지 않은 가상 스레드로 돈다는 데 있다. 어려움 한 회차에 1,000명이 25초 안에 들어오고, 연습이 겹치면 수천 개의 가상 스레드가 동시에 연결 10개를 두고 줄을 선다. 가상 스레드는 싸지만 연결은 그렇지 않다.

함께 차오른 것:

- **MySQL CPU**: 사람처럼 10개부터 평균 128~136%, 순간 최대 208%로 상한(200%) 근처다. 풀을 늘리면 다음에 막힐 곳으로 보인다(추정. 풀을 늘려 재 보지 않았다).
- **백엔드 메모리**: 사람처럼 10개부터 상한 1GiB에 닿았다. 기다리는 가상 스레드와 그 요청들이 쌓인 결과로 보인다(추정. 힙 덤프를 보지 않았다).
- **행 잠금 대기**: 단계마다 100~200회, 합쳐서 1초 안팎으로 작다. 좌석 경합 자체는 막히는 곳이 아니었다.
- **모의 결제 서버**: CPU 평균 10% 안쪽으로 여유가 있었다. 다만 응답 대기 5초를 넘긴 결제가 622건 있었다(아래).

## 이 측정에서 드러난 것(2단계 후보)

- **가상 경쟁자의 동시 실행 수에 상한이 없다.** 연결 10개를 수천 개의 가상 스레드가 기다린다. 가상 경쟁자 실행에 세마포어를 두거나, 회차마다 실행 큐를 두는 것이 첫 후보다. 2단계의 대기열(Redis)과 이어진다.
- **회차가 끝난 뒤의 결제가 많다.** "예매를 확정하지 못해 결제를 취소함"이 28,255건 남았다. 사용자가 성공하거나 매진되어 회차가 끝난 순간 결제 중이던 가상 경쟁자들이 확정 단계에서 거절되고 결제가 취소된 것이다(규칙대로의 동작이다). 결제를 부르기 전에 회차가 끝났는지 보면 결제 호출 자체를 줄일 수 있다.
- **결제 응답 대기 초과 622건.** 모의 결제 서버의 CPU는 여유가 있었으므로, 백엔드 쪽 HTTP 클라이언트 연결이나 확정 단계의 커넥션 풀 대기가 원인일 수 있다(추정).
- **연습 시작이 느려진다.** 회차마다 좌석 1,008행을 넣는다. 사람처럼 20개에서 p95 7.2초다.
- **동시 연습 상한이 난이도를 구분하지 않는다.** 쉬움(200명·5분)은 어려움보다 훨씬 가볍지만 같은 한 자리를 차지한다.

## 정한 것

- **동시 연습 상한을 10에서 5로 낮춘다**(`booking.max-active-performances`). 어려움으로 가정한 가장 나쁜 경우에 5개는 p99 3.1초, 풀 대기 평균 80이었고, 10개부터 p95가 10초를 넘었다.
- 이 값은 이 장비와 이 컨테이너 상한에서의 값이다. 2단계에서 위 후보를 하나씩 고치며 같은 스크립트로 다시 잰다.

## 재현

```bash
BOOKING_MAX_ACTIVE_PERFORMANCES=1000 docker compose up -d --build
load/run-baseline.sh                                    # 곧바로 누름, 동시 연습 5·10·20·40
VUS_LIST="5 10 20" THINK_SECONDS=10 load/run-baseline.sh  # 사람처럼
```

원자료(k6 요약 JSON, 5초 표본)는 `load/results/<날짜>-raw/`에 남고 저장소에는 넣지 않는다.

## 확인하지 못한 것

- 곧바로 누름 5개가 10개·20개보다 나빴다(풀 대기 최대 2,085). 서버를 띄운 직후 첫 단계였고, 연습 5개가 같은 순간 열려 가상 경쟁자 5,000명이 25초 안에 몰렸기 때문으로 보지만, 같은 조건으로 다시 재 보지 않았다.
- 단계마다 한 번씩만 쟀다. 편차는 모른다.
- 풀 크기를 바꿔 보지 않았으므로, 풀을 늘렸을 때 다음에 막히는 곳이 MySQL CPU인지는 추정이다.
